# Admin panel (`/admin`)

Staff page of the site: independent Game and Workshop status, live moderation over RCON, persistent game settings, AI budgets, staff roles, map history, statistics administration and an audit log. Code: [admin.ts](../src/lib/admin.ts) (roles, validation, API), [gun-balance.ts](../src/lib/gun-balance.ts) (server catalog and overrides), [ai-limits.ts](../src/lib/ai-limits.ts) (money policy), [workshop-ai-policy.ts](../src/lib/workshop-ai-policy.ts) (Workshop AI settings), [workshop-ai.ts](../src/lib/workshop-ai.ts) (browser-safe AI types), `src/lib/rcon.ts`, `src/pages/api/admin/[...path].ts`, `src/pages/admin.astro`; storage in the statistics DB (`src/lib/stats.ts`, schema v7). Tests: `test/admin.test.mjs`, `test/gun-balance.test.mjs`, `test/body-part-form.test.mjs`, `test/ai-limits.test.mjs`, `test/workshop-ai.test.mjs`, `test/ai-budget-form.test.mjs`, `test/maps-admin.test.mjs`, `test/rcon.test.mjs`, `test/stats-admin.test.mjs`, `test/names.test.mjs`.

**Gun balance, native map history and isolated-copy integration below are implemented in the working code, pending release/deployment and game acceptance.** Selecting an archive head and applying it to a running game are separate operations.

The landing page header (`src/pages/index.astro`) shows the signed-in player's nickname and, only when `siteIdentity()` (`src/lib/admin.ts`) reports any staff role, a button straight to `/admin` — both rendered server-side from the session cookie, so they are in the first response and never swap in after hydration.

## Interface

Routine actions use Russian labels instead of UUIDs or command strings. Weapon settings show Russian labels, data keys in row titles and nested JSON; map history exposes version digests. One permission-filtered navigation list has three groups: «Операции» (overview, players, matches), «Игра и карты» (game settings, weapons, workshop, statistics), and «Управление» (performance, team, action journal, owner console). Builder opens the Workshop for assigned maps, moderator opens Players, and admin/owner open Overview. Unknown or forbidden hashes return to that role's permitted default.

Builders can create branches, commit and request review within their map scope. Game and Workshop run independently.

Workshop reads top to bottom as one workflow and avoids Git words where a plain one exists: «версия» is a commit, «сохранить версию» commits, «версия в игре» is protected main, «принять в игру» merges a review, «вернуть в игру» restores an old main version as a new commit. Branches keep the word «ветка»; `work-<session UUID>` branches are named by the session that owns them («ветка сеанса от …, автор»), and hashes stay only as dim secondary text. The tab shows: a status card with the shared Workshop switch (the same actions as Overview, feedback in the card); a four-step «Как правка попадает в игру» note; «Ждут решения» with only pending reviews (Проверить и принять → Что изменилось → Тестовый матч → Отклонить) and decided ones folded into «Решённые заявки»; «Карты», one disclosure per catalog map plus the legacy hub. A map summary names the version in the game, the builders and the «Ждёт решения» / «Открыта в мастерской» / «Выключена для матчей» badges. Inside: «Черновик в мастерской» for the map's branch in the verified open session («Сохранить и отправить на проверку» commits, re-reads the catalog and reviews the fresh branch head; «Только сохранить версию»; «Отправить последнюю версию» while a saved head is ahead of the game and not yet pending; rename folded away), builders («Выбрать строителей»), availability, «История версий» and a folded «Ветки и сравнение версий». «Вернуть в игру» is offered only for versions reachable from the published head through `parents`; branch-only versions are marked «Ещё не в игре» and reach the game through review. Merge previews say «Сейчас в игре» / «В присланной версии» and label region files and markup fields by map area. Each map part keeps its own status line across re-renders. «Новая карта» is folded; the AI disclosures sit at the end; «Обновить доступ» appears only while the member list drifts.

Operational sections use rows rather than equal-height card grids. Settings and weapon controls commit on change, one request at a time per form, with a field status and an undo toast. A 409 refreshes untouched controls and retries once with the latest revision. Older snapshots cannot replace a newer saved baseline or receipt; undo is dropped if its saved value has since changed. The receipt line shows the revision, application result, editor and time; field confirmation does not wait for server pickup. Workshop messages commit on blur or after 1.2 seconds idle, with undo when a previous message exists. Kit controls use the same save-on-change/blur model and per-control idle delay, merging only the committed fields into fresh settings and keeping unrelated invalid drafts for correction. Catalog refreshes recheck focus, queued saves and dirty drafts after fetching; older revisions cannot replace kit baselines. Destructive actions use a native `<dialog>` with Escape cancellation and focus restoration. `<select>` uses the keyboard-accessible `customSelect()` over a hidden native form control. The same navigation wraps on mobile; controls use the console’s 36px height.

- Display names for class, map, mode and campaign ids, balance labels/groups and the game-file balance defaults live in `src/lib/game-names.ts`, a hand-kept copy of `blockfield-server/server/lobby/blockfield/{classes,campaigns,maps,modes}`. Update it when the server adds content; unknown ids show a neutral label and are preserved on save. A test checks that every `BALANCE` key has a label and a default.
- ParCool action ids and their Russian labels are `PARCOOL_ACTIONS` in `src/lib/game-names.ts`, a hand-kept copy of ParCool's action enum (not modpack content, so it does not follow the "unknown ids preserved" rule above: the site only ever writes ids from this list).
- Read-only API additions: `GET bans` (`ban`): the latest successful site ban/pardon per nickname from the audit log (in-game bans are not listed; «Разбанить» by nickname covers them). `GET results` rows carry `mapId`, `players:[{uuid,name,team}]` (sorted by score, UUID-like names resolved or «Неизвестный игрок») and `winnerName`. `POST rcon` `stop-room` returns and audits the room's name and map; `POST results/void` audits the match mode, map and time. `overview.rooms.online` is the proxy's online count when it reports one.
- General game fields keep "absent = server default": values equal to the displayed default and untouched class lists are omitted (`src/lib/settings-form.ts`, tested). The weapons tab shows every field with its effective value (override, else gunpack default); editing a value back to the default or clearing the input drops the override. Each overridden field carries an «изменено» badge and a small ↺ button («Вернуть значение ганпака») restoring the default. Plain tunables sit in «Основные» with short hints, ordered damage first (base damage used only when no per-distance table is set, per-distance table with an open-ended last band and inline finals against the match kit, armour piercing, head multiplier, body multipliers, then fire rate, magazine, reload, ammo); bullet physics and other complex or rarely used settings hide in the collapsed «Дополнительно» block per weapon, with no per-field enable switches or «Значение ганпака» accordions. Every setting renders by its schema type (number, checkbox, select, nested group, keyed entries, list with «+»/«×»); there are no JSON textareas anywhere, nullable values use a meaning-labelled switch («Не использовать доп. урон», else «Не задано (как в ганпаке)») and empty means «по умолчанию». Damage fields carry a hover/focus hint with the final damage against a player in the standard match kit (`src/lib/gun-damage.ts`, tested). Undo displays the effective previous value and restores the original override, including its absence. Live catalog refreshes preserve focused and dirty weapon fields. Reset confirms «Вернуть этому оружию значения ганпака?» and commits once. Weapon overrides commit separately; a general settings save preserves them when it omits `gunBalance`.
- Player and admin pages show the visitor's local time with the zone labelled; relative times («5 минут назад») are used in lists. The leaderboard and season boundaries stay UTC and labelled; server logs are UTC.
- Owner rows fall back to the Drasl name, then the last known profile name, then the signed-in owner's own name, then «Неизвестный игрок».

Open admin pages share one `EventSource` connection to `GET /api/admin/events`; reconnect delay is 3 s. Send `POST /api/admin/presence {tab}` every 30 s and when changing tabs. Event updates preserve focused controls and queued changes and advance the revision used by the next commit. Rooms events also refresh Game readiness, headline and lamp from the last status/session without another fetch. Map availability actions await the settings receipt stream, with one recovery GET after 30 seconds. Lists still load through their GET routes.

## Roles

The site is the source of truth for roles. Identity is a server-side session: the `bf_session` cookie holds only a random id, mapped in `site_sessions` to the Drasl API token (AES-256-GCM sealed with `BLOCKFIELD_SESSION_SECRET`) and the account's player UUID, stored without dashes in lowercase. Logout deletes one session, password change deletes all of them and rotates the Drasl token.

| Role        | Can                                                                                                                                                                                                                                                                          |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `builder`   | open `/admin`, see status, rooms and map history; create branches, commit and request review within their map scope                                                                                                                                                          |
| `moderator` | + RCON moderation (`list`, `say`, `kick`, `bf team kick`, `bf stop room`, `bf class lock/unlock`, `range`), map create/rename, maintenance/workshop message                                                                                                                  |
| `admin`     | + `ban`/`pardon`, maintenance/recover, Workshop session/test transitions, game and weapon settings, statistics admin, audit log, grant/revoke builder/moderator, workshop sync, protected-main merge, append-only restore and map export, server performance (`diagnostics`) |
| `owner`     | + grant/revoke `admin`, raw RCON console (`rcon-raw`), every AI money and model setting (`ai`)                                                                                                                                                                               |

Permissions are one map in `src/lib/admin.ts` (`can(role, permission)`); every API route checks it on the server, the page only hides what the role cannot use.

- **Bootstrap:** `BLOCKFIELD_OWNER_UUIDS` (comma-separated player UUIDs, dashes optional) are always `owner`. They are not stored and cannot be changed from the UI. Everybody else needs a row in `staff_roles`. No env and an empty table = nobody has access.
- Admins manage only builder/moderator; owners also manage admin. Nobody changes their own role. Grants resolve the nickname through Drasl's public profile lookup `GET <DRASL_URL>/account/users/profiles/minecraft/<name>` (`{id, name}`, 404 if unknown); owner names through `GET <DRASL_URL>/session/minecraft/profile/<uuid>`.
- **Workshop ACL is derived.** After every role change (and on «Обновить доступ», shown only while the list drifts) the site writes a `members` inbox request with all staff and owners mapped `owner|admin → admin`, `moderator → lead`, `builder → builder`. The site no longer reads `members.json` for auth; it only displays whether the controller's `members.json` matches (drift) and the result of the last sync.

## Contracts

- `GET events` (`view`): SSE, `Cache-Control: no-store`, `X-Accel-Buffering: no`, `retry: 3000`, comment ping every 25 s. Named events carry JSON `{type,at,...payload}` (`at`: UTC epoch milliseconds); published events have an opaque SSE `id`. `Last-Event-ID` replays newer permitted events from the last 200 in this Node process, best-effort; process restarts or older cursors require GET recovery. Each connection also receives fresh `status`, permitted `settings`, and `presence` snapshots without advancing its replay cursor. Watchers and room/presence timers run only while subscribed; missing export directories do not prevent connection.
- Event payloads: `status` `{status,session,rooms}` equals `GET overview` (also refreshes on candidates/maps/members exports); `rooms` `{rooms}` carries the same room status object, compared every 5 s; `settings` `{settings,applied}` equals `GET settings` without balance/catalog, plus `gunBalance:true` when the catalog file changes, plus `kits:true` when the kit catalog changes; `audit` `{entry}` is the exact newly stored `GET audit` row, including numeric `id`, `at`, JSON-text `detail` and numeric `ok`; `request` `{id,result}` carries a controller request id and its result file; `presence` `{presence:[{uuid,name,role,tab,at}]}` lists recent staff heartbeats. `audit` requires `audit`, `settings` requires `settings`, other events require `view`.
- `POST presence {tab}` (`view`): `tab` matches `^[a-z-]{1,24}$`; returns `{presence:[...]}`. Identity and role come from the session. Publishes on membership or tab changes; entries expire after 90 s, pruned on heartbeat and every 30 s while subscribed. Disconnect removes an actor only after their last SSE stream closes. Presence is transient and is **not audited**, including invalid/refused heartbeats.
- Game and Workshop run independently. `admin/status.json` schema 1 describes the actual Workshop lifecycle in top-level `phase`, `gate`, `desired` and `revision`; additive `game:{phase:game|STARTING|UNAVAILABLE,gate:public|closed,release:string|null}` reports independently observed Game readiness. A missing or malformed Game export is not shown as ready. Workshop startup, tests and errors do not close Game admission. `public.json` top-level `mode:game|maintenance` controls only Game; additive `workshop:{mode:workshop|maintenance,message}` reports Workshop admission. The site ignores this additive field when deciding whether to query Game rooms.
- Inbox request: `{schema:1, id, kind, actor:{draslId,name}, createdAt, ...}`; `mode` `{profile: game|workshop|test, expectedRevision, recover?}` (recover only with the legacy `game` request, admin only), Workshop `message` `{message}` (one line, ≤200 chars), `members` `{members:[{draslId,name,role,maps?}]}` (full replacement, generated by the site only; `maps` is only ever set on a `builder` entry — see «Workshop map access» below). The legacy `game` target resumes the selected persistent Workshop editor session; it does not stop Game or disable Workshop. Controller results arrive as `request` events; `GET request?id=<id>` remains available for recovery. `wake` carries no parameters and starts the stored Workshop goal when it sleeps (`POST wake`, any staff role; an unanswered `wake` already in the inbox is reused).
- Workshop sessions: `mode` toward `workshop` carries `session: new|resume` and, only for `new`, `maps: string[]|null`. The site validates actual exported catalog IDs; the controller independently checks its real catalog. `new` optionally carries `branches:{mapId:branchName}` for exactly the selected maps; without it the controller creates `work-<session UUID>` branches. In canonical mode, `null` is frozen to the current explicit map list and every selected map is prepared in an isolated working copy before restarting Workshop. `resume` preserves the same copy and map list; it does not rebase edits onto a newer head. `admin/session.json` `{schema:1,id,maps,branches,startedAt,startedBy,selectionDigest}` is the source of truth. `resume` optionally accepts `sessionId` from a saved draft; it never carries map or branch overrides. The controller checks the immutable archived binding and retained copies before stopping the current editor. Saved rows are paged through the read-only `sessions` inbox kind (`offset`, optional `limit` up to 100); missing or corrupt old copies are refused rather than recreated. The legacy `hub` access scope is not a map version; the runtime lobby map is `lobby`.
- Closed test matches: `mode` toward `test` carries `candidateId`, offered from phase `workshop` with `gate:builders` on a pending candidate. Only Workshop restarts into the isolated test profile. The controller exports `desired.candidate` as the derived package SHA256, not the candidate ID. From `test`, «Вернуться в мастерскую» sends `mode workshop session:resume`; After a Workshop error, «Восстановить мастерскую» sends the legacy `mode game recover:true`; both preserve the selected editor session and map list.
- `settings.json`: `{schema:1,revision,updatedAt,updatedBy,lobby?,rooms?,deathmatch?,classLocks?,classCosts?,campaignBalance?,parcool?,gunBalance?}`. General `PUT settings` replaces ordinary sections; absent keys use server defaults. An omitted `gunBalance` preserves its current value. Both settings save routes require the current `expectedRevision`; stale saves return 409. Ranges: `pvpCooldownSeconds` 0–600, `maxRooms` 1–16, `idleCloseSeconds` 30–3600, `abandonCloseSeconds` 5–600, `deathmatch.minPlayers` 1–24. Campaign rules come from `BALANCE` in `admin.ts`; merged minimum team size cannot exceed maximum, and kill radius cannot exceed warning radius. `applied.json` `{revision,attemptedRevision?,appliedAt,errors,gunBalance?}` reports the server's actual result. Deathmatch and campaign rules affect new matches, not matches already running.
- `parcool`: `{allowedActions: string[]}`, ids from `PARCOOL_ACTIONS` (`src/lib/game-names.ts`), no duplicates. Section present → exactly those actions are allowed, everything else forbidden (`allowedActions: []` forbids every parkour action). Section absent → the mod's base image file governs (currently `FastRun`, `ClingToCliff`, `Crawl`); the mod skips unknown names and reports them in `applied.json`. The UI has one toggle («Задать список действий на сайте»): off omits the section from the save entirely — even if it was set before, since every save replaces the whole file — and shows the checkboxes, disabled, reflecting the base file's own default so the effective value stays visible; on writes the checked ids. `ClimbUp` is the pull-up out of a cliff cling — without it, clinging only holds the player in place.
- Workshop map access: a `builder` row in `staff_roles` (schema v6) carries an optional `maps` array of access scopes (actual exported catalog IDs plus the legacy `hub` scope). Missing/`null` grants every scope, including future ones; `[]` grants no editing scope. This ACL is separate from the frozen selected-session map list. `workshopMembers` drops `maps` for lead/admin roles. `POST /api/admin/staff/maps {uuid,maps:string[]|null}` (`roles`: admin/owner) validates known scopes and uniqueness, then syncs the controller member list. `POST staff/map-access {mapId,uuids}` updates one scope for all builders: granting preserves an existing all-scopes ACL; revoking from all expands the remaining known scopes. Neither operation silently grants future maps through an explicit list.
- RCON: one connection per call, 5 s timeout. Only fixed command shapes from `rconCommand()`; nicknames `^[A-Za-z0-9_]{3,16}$`, room UUIDs, class ids, and free text ≤120 chars with control characters and `§` replaced, never starting with `/`. `range` is sent as `bf range <op>`. A reply starting with `Unknown or incomplete command`/`Unknown command` or containing `<--[HERE]` is reported as a failure. Connection errors reach the browser only as «Игровой сервер не отвечает»; the details go to the server log and the audit entry. `stop room … win RED|BLUE` is sent as `win RedTeam|BlueTeam` (the game's team names). A bare stop reason cannot start with `win`/`draw`. `drain`/`resume` toggle whether new matches start (`bf maintenance drain|resume`); the block shows entry state from the host gate file (read-only) plus drain state from `bf maintenance status`. Interrupt sends `bf maintenance interrupt` and `… confirm <reason>` on the same connection (the game requires the same sender within 60 s).
- Raw console (`POST /api/admin/rcon/raw {command,target?}`, `rcon-raw`: owner only; `src/lib/console.ts`): one command per call through the same `rcon()`. The command must be a string without control characters (newlines included), at most 1000 characters after trimming; leading `/` is removed. The reply is returned whole with `§` codes stripped: `{command, output, rejected, target}`, where `rejected` marks a Brigadier refusal (see above). Connection errors behave like other RCON calls. Audit action `rcon:raw`: target is the redacted command, detail the first 500 characters of the redacted reply and `rejected`; the owner-only response stays whole. The shared `redact()` runs before truncation/storage, also for an invalid command. Refusals (403) are audited without the command, because the body of a refused call is never read. The page confirms commands matching `dangerousCommand()` (`stop`, `op`, `deop`, `ban`, `kick`, `kill`, `whitelist off|remove`, `execute`, `fill`, `gamerule`, `bf maintenance|stop`, …) with the native dialog; this is a UI guard only, the owner's server-side permission is the boundary. History (↑/↓) lives only in the open page. The owner selects `game` (default) or `workshop`; routing uses separate `BLOCKFIELD_WORKSHOP_RCON_HOST/PORT/PASSWORD` for Workshop and records the selected target in the audit detail.

- Workshop scopes: access lists include arena IDs, `lobby`, `limbo` and the legacy `hub` building scope (`WORKSHOP_PLACES` in `src/lib/game-names.ts`). `null` means every scope; an explicit list grants only those listed.
- `POST /api/workshop/access {actor, target, mapId, allowed}` (`src/pages/api/workshop/access.ts`, `handleWorkshopAccess`): called by the workshop server when an admin uses «Разрешить/Запретить строить» on the tablet. `Authorization: Bearer BLOCKFIELD_WORKSHOP_KEY` (constant-time compare; no key = 503), then the in-game actor's own site role must have `roles`; the target must be a builder. Applies `withMapAccess`, re-syncs the workshop `members` request and writes `workshop-map-access` to the journal with `from: 'game'` (refusals too).

### Weapon balance

`GET /api/admin/gun-balance` (`settings`: admin/owner) returns `{available:true,catalog}` or `{available:false,error}`. `GET settings` includes the same availability beside `settings` and `applied`. The server writes `gun-balance.json` next to `settings.json`: `{schema:1,revision,fields,guns}`. Each gun has its index `id`, shared `data` ID, `name`, `type`, complete `defaults`, current `effective` values and baseline `warnings`.

The recursive `fields` metadata describes all 33 synchronized native root fields of pinned TaCZ bf7, including `bullet`, `reload`, `recoil`, `heat`, `charging`, attachment maps and script parameters. It also exposes the server-only `body_part_multipliers` described below. It supplies types, bounds, enum values, nullable fields and supported unions (`infinite`, legacy ignite boolean). Native nested values are edited as JSON; kit weapons are listed first, with search across the full catalog. Defaults and metadata come from the server, not a copied ganpack in the site. Enum-map defaults use wire keys such as `aim`, `semi` and `scope`, without duplicate uppercase enum names. Missing or invalid catalog data disables saves (503) rather than inventing defaults.

`PUT /api/admin/gun-balance` takes `{expectedRevision,gunBalance}` and returns `{settings}`. It preserves every unrelated settings section. Keys are gun **index IDs**, for example `elitex:ak47`, not data filenames:

```json
{
  "expectedRevision": 7,
  "gunBalance": {
    "elitex:ak47": { "draw_time": 0.82 },
    "tacz:glock_17": { "bullet": { "damage": 9 } }
  }
}
```

Only changed fields are stored. Objects merge recursively; arrays replace the whole value. Remove a field or gun to restore current ganpack/datapack defaults; an omitted or empty `gunBalance` on this dedicated route resets the whole section. A general settings save omitting it preserves it. `null` disables only a metadata-nullable value and is not a reset; `gunBalance:null` is invalid. Multiple explicit native overrides sharing a `data` ID must produce identical effective native data. Body-only entries do not claim or reset native data. Old baseline values outside edit bounds stay readable and resettable; changed values must satisfy the metadata.

#### Body-part damage

The existing `gunBalance` route also stores per-weapon `body_part_multipliers`: `head`, `torso`, `left_arm`, `right_arm`, `left_leg`, `right_leg`. Each coefficient is finite, numeric and between 0 and 10; missing values mean 1. `null`, unknown parts and nonnumeric values are refused. Six labelled numeric controls replace raw JSON for this field. Removing the field/weapon/section restores all relative coefficients to 1. There is no separate limb health or injury system.

TaCZ uses its gun **index ID**, for example `elitex:ak47`. Registered item weapons use the typed key `item:<namespace>/<path>`, for example `item:superbwarfare/ak_47`. LR throwable weapons use their exact data index as `throwable:<namespace>/<data-path>`, for example `throwable:lrtactical/smoke_grenade`, because multiple weapons share the registry item `lrtactical:throwable`. The supported LR dagger uses `melee:lrtactical/dagger` with source ID `lrtactical:dagger`; the shared registry item `lrtactical:melee` cannot identify a particular melee weapon. All three typed kinds permit only body multipliers and do not claim native aliases. Catalog rows add `weaponKind:tacz|item|throwable|melee` and their canonical `sourceId`; typed rows have `data=id`, `type=weaponKind`, and only body multipliers in `defaults/effective`. TaCZ rows retain native values as well. All six body defaults equal 1. The existing catalog is still authoritative: the site cannot invent a supported item/index or infer combat support from a translation key. LR throwable coefficients affect direct hits; explosion, fire and splash retain native damage. The LR melee row covers only the dagger's exact-hit adapter under Blockfield's knife-only melee policy. Karambit and baseball-bat cone/area adapters are unsupported and have no catalog rows or body-part controls; the existing policy suppresses their native attacks.

Body coefficients belong to each weapon index, including aliases sharing native TaCZ data. Native overrides for those aliases must still agree. The mod strips this field before building native TaCZ JSON or client deltas and applies its coefficient exactly once after the normal weapon damage, including native head/leg rules. No hidden global coefficient is multiplied on top. The additive `bodyPartsEnabled` catalog flag reports the actual server acceptance gate; `false` permits preparing coefficients but does not claim that body damage is active. The gate remains disabled pending game acceptance.

### AI money budgets

The compact «Бюджет AI» disclosure and the «AI мастерской» form inside «Мастерская» are owner-only. The reader tolerates old files that only carry the switch and models (missing limits fill in from mod defaults) and ignores unknown future keys; only broken JSON or mistyped values fail closed. `GET /api/admin/ai-limits` returns `{policy}`; `PUT` uses `{expectedRevision,mode,sessions?,builders?}` and returns the saved `{policy}`. `GET /api/admin/workshop-ai-settings` returns the stored `{settings}` (mod defaults at revision 0 when never configured); `PUT` takes the full `{expectedRevision,enabled,provider,generationProvider,guardProvider,transcriptionProvider,providers,inputGuardEnabled,generationModel,guardModel,transcriptionModel,cleanupModel,cleanupProvider,maxBlocks,blocksPerTick,minimumBuildTicks,applyBudgetMs,hourlyRequestLimit,hourlyPlayerRequestLimit,maxHourlyBuilders,generationMaxPricePromptUsdPerM,generationMaxPriceCompletionUsdPerM}` and returns the saved `{settings}`. All four routes require `ai`, which only the owner role holds; mutations use the same-origin wrapper, bounded JSON body, server-side role check and audit journal. A map/session owner, a permissive Workshop ACL or a site admin cannot authorize a write. Running an AI request gives an owner no budget exception. The model list, request quota and tariff ceilings carry no business allowlist: any well-shaped vendor/model works, limits apply to the generation model only, and enabling still needs a key for every referenced provider: OpenRouter through `POST /api/admin/workshop-ai-key` (inbox kind `ai-key`, status `ai-key.json`), the gateway key from a host file, custom registry ids through `POST /api/admin/workshop-ai-provider-key` with `{provider,key}` (inbox kind `ai-provider-key` with the same 0600 envelope, status `<id>-key.json`). `providers` holds at most 8 `{id,label,baseUrl}` entries (id `a-z0-9-`, not a preset id; baseUrl absolute `https://` without credentials, query or fragment, ≤200 chars); every referenced provider id must exist or the save fails closed. Missing per-model providers follow the legacy `provider`; an empty `cleanupModel` means cleanup is off and `cleanupProvider` follows transcription.

The independent `ai-limits.json` in `BLOCKFIELD_SETTINGS_DIR` has a closed schema:

```json
{
  "schema": 1,
  "revision": 1,
  "currency": "USD",
  "mode": "session",
  "sessions": { "11111111-1111-4111-8111-111111111111": 10000000 },
  "builders": { "22222222-2222-4222-8222-222222222222": 2000000 }
}
```

Amounts are nonnegative **integer microUSD**: 1 USD = 1,000,000 microUSD, with a maximum of 1,000,000,000,000 per grant. Each map allows at most 256 canonical lowercase UUIDs with hyphens. Budget 0 or no grant denies requests. `session` shares the exact selected Workshop session's allowance across participants; `builder` uses the participant's stable UUID. UI choices come from the existing verified session catalog and site staff/owners; Drasl UUIDs are normalized before writing. Dollar input accepts up to six decimal places, including a decimal comma, and converts exactly without floating-point rounding.

Policy revision is independent of Game settings. Amounts set the **total spending allowance**, including money already spent; saving is not a top-up. Builder accounts persist across Workshop sessions. Present grant maps replace their stored maps; omitted maps remain intact, so changing only `mode` preserves both. Stale writes return 409 with the form draft intact. General `PUT settings` cannot change this file. A missing policy displays empty deny grants at revision 0; malformed, oversized or inaccessible policy data returns 503 and cannot be silently replaced. Mode switching, grant removal/re-addition and restarts do not erase persistent spend or give a fresh allowance automatically.

Before the input guard, the preparation runtime reserves the whole generation job from the owner's configured tariff ceilings and the request/token bounds, so a request the tariff probe and max_price routing accept always fits its reserve. These conservative bounds cover the sized generation input, output including reasoning, and semantic guards at the configured ceilings. The `maxBlocks` hard limit remains 32768, with selection axes at most 128. Only confirmed provider cost settles as actual spend. Remaining budget below the complete reservation denies generation before a paid provider request; owners have no bypass and only the owner (permission `ai`) can raise a grant. The reservations are conservative preparation bounds, not displayed prices or promises of actual cost. Isolated native acceptance passed a 20-floor highrise with progressive Apply and complete Undo at the middle tier 8192; the upper tier 16384 and production integration remain unaccepted, and AI stays off by default. Reservation bounds, exact model/API compatibility and current provider prices must be revalidated before enabling this feature. Uncertain results retain reserved liability without repricing or reset. Provider credentials stay server-side, using ordinary OpenRouter credits without BYOK; the browser contains no API key.

Voice uses the owner's configured transcription model with no allowlist and no tariff probe: the duration-sized reserve is topped up to the authenticated cost and never refuses or blocks. Whisper is [priced at $0.006/minute on 2026-10-08](https://openrouter.ai/openai/whisper-1/pricing), with nearest-second billing. The server derives duration from validated PCM bytes and rounds seconds up; generation is charged separately and keeps its own reservation. The input guard likewise carries no price caps or provider pin: its cost is accounted exactly. Only the generation model is limited (owner-configured request quota and per-token tariff ceilings); helper calls never block paid work. The recognized text only fills the editable request.

Persisted usage and application receipts are not yet exported to the site. The UI reports **saved policy only**, never invented current spend, remaining money or runtime application. Server preparation and acceptance details belong to the mod/workspace contracts.

The server polls settings every 5 seconds, validates the entire revision and sends a dedicated `blockfield:gun_balance` delta to online clients immediately after applying it. It does not run `/reload` or `tacz reload`, refill magazines, or restart draw/reload/bolt actions. Models, animations, sounds and Lua are outside this update. A join receives complete effective data; a natural TaCZ reload recaptures genuine defaults and reapplies overrides. A hot update is refused if an online client lacks delta support.

A saved file is not proof of application. In `applied.json`, `revision` is the last applied revision; `attemptedRevision` identifies the attempt. A gun update rejected as a whole reports the previous `revision`, the rejected `attemptedRevision`, and field errors. `settingsReceipt()` in `settings-form.ts` recognizes that result immediately rather than waiting for the new revision to become applied. Normal reports set both revisions to the same value. `gunBalance` reports `{revision,changedData,onlineUpdated,reloadError?}`. Type, range, alias or server invariant errors preserve previous data. A 409 means reload settings before retrying. Mod details and acceptance scenarios: [admin-settings.md](https://github.com/Blockfield/blockfield-mod/blob/main/docs/admin-settings.md).

Isolated-stand evidence on 2026-09-30: the primitive draw gate was changed from about 0.32 s to 3 s and reset to its baseline without a reload or reconnect. The fresh-JAR catalog exposes 91 guns and 33 fields and passes site validation, including enum keys. An invalid whole revision preserved the previous data and reported `attemptedRevision`; valid apply/reset each reported one online update. Other fields need their own game scenarios. This is stand evidence, not production deployment.

### Equipment kits

The «Наборы» tab is admin/owner-only. `GET /api/admin/kits` returns a bounded authoritative `kits.json` catalog or `{available:false,error}`. It contains the runtime revision, effective and release-default definitions, item/gun/ammo/attachment/throwable registries, accessory slots, field bounds and mode metadata. `defaultFixedKitId` describes reset behavior separately from current `fixedKitId`; `supportsFixedKit` keeps training visibility separate from combat-mode fixed grants. Missing or malformed catalogs disable saves.

Native forms edit kit names, mode visibility (including training), deployment cost, player limit, knife position, stable variants and their item order, typed weapon/ammo/attachment/grenade choices, armor, shared/team/variant accessories and bounded drone settings. Item panels render lazily; large registries use bounded searchable suggestions. Raw NBT and JSON editing are unavailable. Existing release kits reset to defaults; deleting a custom kit removes its override. Fixed assignments offer the runtime default, menu selection, or any kit allowed in that combat mode. Fixed modes grant that kit for free without class quota, retaining its price and limit elsewhere. Deleting an assigned kit or hiding it from the mode requires fixing that binding before saving.

`PUT /api/admin/kits {expectedRevision,kits,fixedModeKits}` stores full changed definitions and explicit binding overrides in the existing `settings.json`. It preserves every unrelated settings section. A general settings save preserves these two sections when omitted. The site validates exact registry IDs, structured metadata, bounds, duplicate IDs and assignments; the game independently validates the whole revision before changing its known-good definitions. Controls autosave with a queued write and undo. A stale revision refreshes the settings and retries once, preserving the local form draft. The live `applied.json` receipt reports application separately: storage alone does not establish runtime application. New grants/refills use confirmed definitions; current inventories are not replaced on save.

### Map branches, review and isolated copies

Published arena rows have an admin/owner availability toggle. `PUT /api/admin/maps/availability {mapId,enabled,expectedRevision}` updates only `disabledMapIds` in the current settings, preserving every other section. It refuses unknown/private/non-arena IDs and stale revisions before writing. Existing canonical future IDs in the disabled list remain intact. `GET maps` exposes desired availability plus the bounded applied set; the UI never derives successful runtime application from a write alone. A malformed settings file disables this write rather than replacing it with defaults.

After a live settings receipt confirms the new revision and exact applied set, disabled maps disappear from new Game matches and training entries. Already started matches and campaigns, including their later stages, finish normally. Workshop drafts and private tests remain available; availability does not change history, branches or published heads. The toggle waits for the receipt, reports rejection or an unconfirmed timeout, and keeps saved world data untouched.

`GET /api/admin/maps` (`view`) reads the controller catalog and returns `{available:true,maps,session?,editableMaps,sessions?,sessionsTotal?,sessionsNext?}` or an explicit unavailable error. Each map carries its immutable versions, the active `head`, and named `branches`. The protected `main` ref is derived from that head, never a second mutable pointer. Versions retain legacy `parent` and add `parents` (two parents for a merge). Branch refs bind a version digest, generation, optional working-copy UUID, author and time. Catalog parsing rejects malformed references, parents and session bindings.

Builders may create branches, commit, compare and request review only in their site-assigned map scope; moderator/admin/owner inherit editing. Only moderator and above activate an editor session. Protected-main merge, rejection, export and restore remain admin/owner actions. The controller independently verifies the exact actor UUID/name, role, map scope and selected copy/branch. All permissions are checked on the server; hiding a button is not an authorization boundary.

«Новая карта» creates an empty arena with an ID, a readable name and a nonempty selection of `campaign`, `room`, `tdm`, `snipers`, `awp`, `deathmatch` and `training`. Moderator/admin/owner may create it. The site generates the new session UUID; a browser cannot select or rebind an old copy. The controller saves the previous editor, retains its dirty archived copy and opens the new private branch by restarting Workshop only. Game keeps running. The inbox result confirms creation; observed Workshop readiness confirms when building may begin. Build and place mode-specific geometry with the in-game tablet, then commit, review, choose a test mode and publish through this panel. No command or JSON editor is required for this path.

The selected draft has a name-only editor. `maps[].draft` carries `{workingCopyId,name}` separately from the published `mapJson`; the UI uses it only for the verified active session. Renaming requires the exact copy and controller revision, saves and restarts Workshop, and changes the draft only. Commit and review are still required before main changes. Invalid names, duplicate map IDs, stale revisions and missing copies fail before enqueueing or under the controller's authoritative lock.

An editor works in its retained session copy on a named branch. «Сохранить версию» snapshots that copy as an immutable commit and moves the branch only when `expectedBranchHead` still matches; the commit message is required and limited to 200 characters. «Сохранить и отправить на проверку» sends one `candidate {commit:true,note}` request bound to the exact selected copy, branch and expected branch head: the controller commits current world/markup edits and freezes the new commit and current main head for review. «Отправить последнюю версию» remains a review of the existing saved commit. Commit and submission never restart Workshop; further editing remains possible. While Workshop sleeps, the controller snapshots the saved copy from disk without starting the editor.

The tablet's `POST /api/workshop/submit` performs the same commit-and-review after shared-key, authoritative site-role, map scope and selected-copy checks. The site supplies `commit:true` and a sanitized note `С планшета: <nickname>` (at most 200 characters). A branch equal to main is allowed: the controller decides whether the working copy has changes. The response `{id}` confirms enqueueing only. The mod must show a pending state, then poll `GET /api/workshop/submit?id=<id>` using the same Workshop bearer key. This returns `{result:null}` while pending, or the validated controller receipt including `ok`, `error` and optional `payload`. Show success only for `ok:true`; for `ok:false`, display the controller's refusal reason (for example no changes or a stale head). Use a bounded polling deadline; an expired wait is unconfirmed, never success. Admin actions already follow the same receipts and display refusals. Both schema-1 and the controller's existing unversioned result envelopes are accepted; unknown schemas are refused.

Roll out the controller supporting `candidate {commit:true,note}` before this site change, then update the tablet label and receipt polling. Otherwise an older controller could review the old commit without saving current edits.

Readable comparisons show changed file digests, region coordinate bounds and exact configuration-field before/after values. Results are bounded to 8 MiB and displayed in pages; an invalid result is an error, never an invented empty diff. A merge preview binds the source and target versions and exposes only readable `changes` and `conflicts`. Each conflict uses its exact path and an explicit `ours` (current main) or `theirs` (reviewed commit) choice. Changing a choice disables approval until the preview is recomputed. Missing choices, stale heads and extra conflict paths are refused by the controller. Git reviews do not accept `force`.

`expectedHead` must match the current main and the review's frozen `targetHead`. If main advances, submit a fresh review of the branch commit. The controller repeats comparisons under its lock. Restore appends a new commit with the current main as parent; it does not rewind history. `maps/rollback` remains an alias. Follow the inbox receipt before refreshing history. Selecting a new main and applying that version to a running service remain separate operations.

A newly created private map has no main: its first review freezes `targetHead:null`. Merge preview and publish require explicit `expectedHead:null`, compare the commit against an empty tree, and create main only when that absence still holds. A later publication racing with it makes the old review stale; omitted or undefined heads do not stand for null. The test dialog reads `supportedModes` from the frozen candidate and sends `mode {profile:test,candidateId,modeId,expectedRevision}`. The site and controller reject unsupported choices independently; current uncommitted mode toggles cannot change which version is being tested.

The saved-draft list shows author, time and map names (a branch only when it is not the session's own) rather than UUID-only links. «Продолжить черновик» sends `mode {profile:workshop,session:resume,sessionId,expectedRevision}` with no overrides. Switching branches or sessions preserves the old isolated dirty copy. «Показать ещё» reaches drafts beyond the first 100 catalog rows without growing every status poll.

Native candidates carry `native:true`, `versionDigest`, `baseVersion`, `workingCopyId`, and initially `sha256:null,size:null`. Acceptance/activation do not create a ZIP. Use «Подготовить ZIP»; the controller exports with pinned zlib 1.3.2 into its HDD cache and reports checksum/size plus `exportReady`. Download uses `GET candidates/download?id=…`: an accepted candidate and a valid SHA256 are required; a missing cache artifact returns 503. If a derived cache entry is evicted, request export again. Mount controller `BF_MAP_PACKAGES_DIR` read-only at `BLOCKFIELD_MAP_PACKAGES_DIR`; do not copy packages into the SSD admin directory.

Runtime application depends on map kind. New arena matches capture the selected immutable version; running matches retain theirs. A lobby head must be captured when starting its world and does not replace a running lobby. A limbo head requires materializing/applying the derived proxy world before controlled proxy startup. These runtime adapters are part of the pending working-code integration: a selected head alone does not establish deployment or game acceptance.

For Limbo, the UI enables «Подготовить для прокси» only with a verified running workshop session. The API validates that the requested immutable version belongs to the Limbo archive, then enqueues `limbo-export`; the controller independently requires exactly one ready workshop instance and reports any refusal in the inbox result. Preparation does not change the head or start, stop or restart either service. Selection or rollback requires that proxy service to be stopped; the controller checks this before changing the head/selection pair. At startup the proxy validates the selection, config, schematic and checksum together. Legacy branchless candidates and overlay metadata remain readable; their historical publication flow keeps its existing base-mismatch confirmation. New branch-aware reviews always use the explicit merge contract above. The old `tools/workshop/fetch-map.py` command is retired. ## Server performance

«Производительность» (`diagnostics`: admin/owner) exists to catch freezes, TPS drops and game errors. Code: `src/lib/diagnostics.ts`; tests `test/diagnostics.test.mjs`.

- `GET /api/admin/diagnostics/live`: vanilla `tick query` over RCON (Minecraft 1.20.3+, no mod): state, target TPS, average and P50/P95/P99 tick time over the server's last 100 ticks. Read-only, not audited. Works today, without a producer.
- `GET /api/admin/diagnostics`: samples of the last 24 h, the newest 500 events, and `lastSampleAt`. No samples or a last sample older than 3 minutes is shown as unknown/stale, never as healthy. The journal filters by kind and text, copies the shown records as text and exports them with the samples as JSON.
- Producer: `POST /api/stats/diagnostics`, the same `Authorization: Bearer <ingest key>` and `X-Blockfield-Server-Id` as match results (env or DB keys, constant-time, authenticated before the body is read, 1 MiB limit); the body's `serverId` must equal the header. Response `{samples, events}` (counts accepted); resends are idempotent (`(serverId, at)` per sample, `(serverId, id)` per event).

```json
{
  "schemaVersion": 1,
  "serverId": "<server UUID>",
  "startedAt": 1759790000000,
  "samples": [
    {
      "at": 1759800000000,
      "tps": 19.6,
      "msptAvg": 21.4,
      "msptP95": 38.0,
      "msptMax": 3400,
      "players": 12,
      "heapUsedMb": 1800,
      "heapMaxMb": 3072,
      "gcPauseMs": 120
    }
  ],
  "events": [
    {
      "id": "<UUID>",
      "at": 1759800000000,
      "kind": "freeze",
      "durationMs": 3400,
      "source": "Server thread",
      "message": "…",
      "repeats": 1
    }
  ]
}
```

A sample summarizes one interval (one minute recommended): `tps` and `msptAvg` over it, `msptMax` its worst tick, `gcPauseMs` time spent in GC. `players`, `msptP95`, heap and GC fields are optional. `kind` is `freeze` (requires `durationMs`), `error`, `crash` or `warning`; `message` ≤ 4000 characters and `source` ≤ 120 after redaction; `repeats` coalesces identical events. At most 120 samples and 200 events per report; times more than 5 minutes ahead refuse the report, items older than retention are dropped. Retention: samples 7 days (cap 50 000 rows), events 14 days (cap 5000, retaining errors/crashes before freezes/warnings, newest within each group). The admin view, local filters, counts and export use the newest 500 retained events, not the complete journal. Before storage `redact()` removes control characters except newline/tab, URLs (webhooks included), e-mails, IPv4/IPv6 addresses, credentials after `password=`, `token:`, `Bearer` and similar (including quoted JSON keys, `rcon_password`, `access_token`, `client_secret`), and long letter+digit runs; canonical UUIDs stay. The producer must still never send secret-bearing logs.

## Statistics administration

- Void/restore a result (`results.voided_at/voided_by`). Voided results leave every leaderboard, profile and history query. A producer replay of a voided result stays voided. Voiding or restoring a rated campaign (campaign, completed/draw) deletes the ratings and rating changes of its season **and every later season** and replays all non-voided rated campaigns from that season's start in `ended_at, server_id, event_id` order through the normal rating code, so later seasons' carry-over stays consistent. Earlier seasons are untouched.
- Ingest keys: `ingest_keys` stores only SHA-256 of the key; the plaintext is shown once on creation. `POST /api/stats/results` accepts env keys (`BLOCKFIELD_STATS_INGEST_KEYS`) or non-revoked DB keys for the same server ID, compared in constant time.
- Seasons are read-only (generated by code).

## Audit

Every non-GET call by a staff member except the transient `POST presence` heartbeat writes `admin_audit` (actor, role, action, target, JSON detail capped at 2 KB, ok, error), including permission refusals and failures. Players without a role are refused before the request body is read and are not audited, so they cannot grow the table. The table keeps the newest 10 000 rows; admin sees the last 200. The attempt row is written before the effect runs (pending, shown as «выполняется»); when the log is down nothing runs. Crash orphans are marked interrupted at boot. High-risk routes (roles, rcon ban/pardon, raw console, mode) fail closed when the finalize is lost; the rest return 200 with an `auditWarning`. Settings bodies and RCON output (first 500 chars) are kept in `detail`; RCON passwords and ingest keys never are.

## Threat notes

- Fail closed: no DB, no owners and no grants, an unknown role, or a Drasl error all mean no access. Owners cannot be demoted from the UI, so a compromised admin cannot lock out the owner or grant admin.
- Only the owner has a raw console (`rcon-raw`, environment-only role). Everyone else sends an action name and arguments, never a command string. Validation rejects newline/space injection in names and leading `/` in text.
- Mutations use the existing same-origin check (`route()`), the `SameSite=Strict` session cookie and `Cache-Control: no-store`. No rate limiting yet (put the reverse proxy in front).
- A stolen session gives that player's role until the Drasl token is reset; revoke the role on the site, which also updates the workshop list.
- The inbox is trusted by the controller: it must still validate requests itself (the site is not the only writer to the host directory).
- The dev identity is ignored in production; never set `NODE_ENV` to anything else in deployed containers.

A recognized account with no admin access is not necessarily a lost login. Check the effective `BLOCKFIELD_OWNER_UUIDS` and selected database first. Owner access is deliberately environment-only; restoring a database does not restore this variable. Persist it in Dokploy and preserve it when updating the application environment.

Repository boundaries and shared files are mapped in [ARCHITECTURE](https://github.com/Blockfield/blockfield-workspace-private/blob/main/docs/ARCHITECTURE.md). Update this contract and that map when their relationship changes.
